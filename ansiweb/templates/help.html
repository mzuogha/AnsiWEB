Where to run AnsiWEB

Run AnsiWEB on a Hyper-V virtual machine or a dedicated server, not on WSL. WSL is fine for trying AnsiWEB out, but it is not built to run a service that has to be there when nobody is signed in.

The three practical choices, best first:

WhereWhat to expect
Hyper-V virtual machine
recommended		 Starts with the host, whether or not anyone signs in, and comes back by itself after a restart or a power cut. It has its own address on your network, so the PCs reach it directly and the firewall rule the prep script creates keeps working. Checkpoints give you a way back if an upgrade goes wrong.
A dedicated machine, or another VM platform Equally good. VMware, Proxmox, XCP-ng or a spare physical box all behave the same way: a service that starts at boot and keeps its address.
WSL on a Windows PC
trying it out only		 Works, but see below: it does not start on its own, its address changes, and everything stops when the signed-in user logs out.

Why WSL is not suitable for real use

    the host at 3am, AnsiWEB is simply not running until somebody signs in and opens a terminal — so the overnight deployment and the update check never happen.
  • It stops when the user logs out. WSL is tied to the signed-in Windows session, so signing out or switching user can take the service down in the middle of a deployment.
  • Its address changes on every restart, which breaks the port forwarding the PCs depend on. The scheduled task below papers over it, but it is one more thing to go wrong unattended.
  • The PCs never reach it directly. Everything is forwarded from the Windows host, so one problem there looks like every PC being unreachable at once.
  • systemd is off by default, and the job runner, the scheduler and the service itself rely on it.

None of this is a fault in WSL — it is a development tool, not somewhere to host a service. If AnsiWEB is on WSL and working there is no urgency, but move it before you rely on scheduled deployments.

Setting up the Hyper-V virtual machine

On Windows 10/11 Pro or Enterprise, or Windows Server. Home editions do not include Hyper-V; VirtualBox, VMware or a spare machine work just as well, and the AnsiWEB side is identical.

1. Turn Hyper-V on (Administrator PowerShell, then restart)

Enable-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V -All

2. Give it a network the PCs can reach

An external switch puts the VM on your LAN with its own address, which is what you want. The Default Switch gives it a private address that changes on reboot, which brings back the WSL problem.

Get-NetAdapter        # find the wired adapter's name
New-VMSwitch -Name "LAN" -NetAdapterName "Ethernet" -AllowManagementOS $true

3. Create the VM

New-VM -Name AnsiWEB -MemoryStartupBytes 4GB -Generation 2 `
       -NewVHDPath "C:\VMs\AnsiWEB.vhdx" -NewVHDSizeBytes 60GB -SwitchName "LAN"
Set-VM -Name AnsiWEB -ProcessorCount 2 -AutomaticStartAction Start -AutomaticStartDelay 30 `
       -AutomaticStopAction ShutDown
Set-VMDvdDrive -VMName AnsiWEB -Path "C:\iso\ubuntu-24.04-live-server-amd64.iso"

-AutomaticStartAction Start is the part that matters: the VM comes back on its own after a restart or a power cut, with nobody signed in. -AutomaticStopAction ShutDown closes Ubuntu cleanly when the host is shut down.

4. Ubuntu needs Secure Boot's Microsoft certificate

Set-VMFirmware -VMName AnsiWEB -SecureBootTemplate MicrosoftUEFICertificateAuthority
Start-VM -Name AnsiWEB
vmconnect.exe localhost AnsiWEB

5. Install Ubuntu Server, then AnsiWEB

Give it a fixed address (or a DHCP reservation), then follow Deploy on Ubuntu Server below, inside the VM. Once it works, take a checkpoint so you can step back if an upgrade misbehaves:

Checkpoint-VM -Name AnsiWEB -SnapshotName "AnsiWEB installed and working"

Deploy on Ubuntu Server (standalone or in a VM)

Ubuntu Server 22.04 or 24.04, 2 vCPU, 4 GB RAM, about 10 GB free for the cache, on a fixed IP address.

Install

sudo apt update && sudo apt install -y git
git clone https://github.com/mzuogha/AnsiWEB.git
cd AnsiWEB
sudo ./install.sh

The installer asks for the first administrator password, then prints the address to open.

Give the server a fixed IP (if it is not reserved in DHCP)

ip -brief address
sudo nano /etc/netplan/50-cloud-init.yaml
sudo netplan try        # reverts by itself if it breaks your connection
sudo netplan apply

Firewall

sudo ufw allow 22/tcp
sudo ufw allow 80/tcp     # installer cache, used by the PCs
sudo ufw allow 443/tcp    # this web interface
sudo ufw enable

Day to day

sudo systemctl status ansiweb          # is it running
sudo systemctl restart ansiweb         # restart it
sudo journalctl -u ansiweb -f          # follow the log

sudo ansiweb plan                      # rebuild inventory and deployment plan
sudo ansiweb update-cache               # check vendors, refresh the cache
sudo ansiweb deploy all                 # deploy everything, everywhere
sudo ansiweb deploy site:HQ             # one site
sudo ansiweb deploy pc:PC-HQ-001        # one PC
sudo ansiweb list-users                 # who can sign in
sudo ansiweb add-user jane operator     # add a user with a lesser role
sudo ansiweb set-password jane          # reset a password

Upgrade

cd ~/AnsiWEB
git pull
sudo ./install.sh

Your configuration, secrets and cache in /var/lib/ansiweb are kept. See the release notes afterwards.

Deploy on WSL (Ubuntu on a Windows PC)

For trying AnsiWEB out, not for running it. WSL does not start with Windows, stops when the signed-in user logs out, and changes its address on every restart, so scheduled deployments and overnight update checks are missed unless somebody happens to be signed in. Why, and what to use instead.

Fine for trying AnsiWEB out. Two extra things are needed: systemd inside WSL, and port forwarding from Windows so your PCs can reach the server. Use a Windows machine that stays on, and not one that AnsiWEB itself manages.

1. Install WSL and Ubuntu (Administrator PowerShell on the Windows host)

wsl --install -d Ubuntu-24.04
wsl --update
wsl --version

2. Turn on systemd (inside Ubuntu)

printf '[boot]\nsystemd=true\n' | sudo tee -a /etc/wsl.conf

Then, in PowerShell: wsl --shutdown. Reopen Ubuntu and check with systemctl is-system-running — "running" or "degraded" are both fine.

3. Install AnsiWEB (inside Ubuntu)

sudo apt update && sudo apt install -y git
git clone https://github.com/mzuogha/AnsiWEB.git
cd AnsiWEB
sudo ./install.sh
hostname -I | awk '{print $1}'      # note this WSL address

4. Forward ports 80 and 443 from Windows (Administrator PowerShell)

$ip = (wsl hostname -I).Trim().Split(' ')[0]
netsh interface portproxy add v4tov4 listenport=80  listenaddress=0.0.0.0 connectport=80  connectaddress=$ip
netsh interface portproxy add v4tov4 listenport=443 listenaddress=0.0.0.0 connectport=443 connectaddress=$ip
New-NetFirewallRule -DisplayName "AnsiWEB" -Direction Inbound -Protocol TCP -LocalPort 80,443 -Action Allow
ipconfig | findstr /i "IPv4"         # the address your PCs should use

Port 80 serves the installer cache to the PCs; 443 is this interface. In Settings, the server IP must be the Windows machine's LAN address, not the WSL one.

5. Keep it working after a reboot

WSL's address changes when it restarts, which breaks the forwarding. Save this as C:\Scripts\ansiweb-wsl.ps1:

wsl -d Ubuntu-24.04 -u root -e /bin/true
Start-Sleep -Seconds 15
$ip = (wsl -d Ubuntu-24.04 hostname -I).Trim().Split(' ')[0]
foreach ($port in 80, 443) {
    netsh interface portproxy delete v4tov4 listenport=$port listenaddress=0.0.0.0 2>$null
    netsh interface portproxy add    v4tov4 listenport=$port listenaddress=0.0.0.0 `
          connectport=$port connectaddress=$ip
}

Then register it to run at startup as SYSTEM:

$action  = New-ScheduledTaskAction -Execute 'powershell.exe' `
           -Argument '-NoProfile -ExecutionPolicy Bypass -File C:\Scripts\ansiweb-wsl.ps1'
$trigger = New-ScheduledTaskTrigger -AtStartup
Register-ScheduledTask -TaskName 'AnsiWEB WSL' -Action $action -Trigger $trigger `
    -User 'SYSTEM' -RunLevel Highest

Preparing a PC

Once per PC, before AnsiWEB can reach it. Download the script from the PCs page — it already has this server's address and the {{ account }} account name in it.

powershell -ExecutionPolicy Bypass -File .\Prepare-AnsibleHost.ps1

Run it in an Administrator PowerShell on the PC and enter the same account password used in AnsiWEB. It creates the local administrator account, enables WinRM over HTTPS and opens port 5986 to this server only. Useful checks on the PC:

type C:\ProgramData\AnsiWEB\prepare-log.txt
winrm enumerate winrm/config/listener
Test-WSMan -ComputerName localhost -UseSSL
tzutil /l                          # valid time zone IDs

Backup and restore

# easiest: Settings -> Download backup

# or from the command line, including the app cache:
sudo systemctl stop ansiweb
sudo tar czf ~/ansiweb-backup-$(date +%F).tar.gz -C /var/lib ansiweb
sudo systemctl start ansiweb

The archive holds the key to your stored passwords, so keep it somewhere safe.

Removing an app from the PCs

Taking an app out of the standard set stops AnsiWEB installing it but leaves it on the PCs. Use the Inventory page to remove it from them: add an entry, press Preview to see the exact command per PC, then type REMOVE to run it. A normal deployment never uninstalls anything, so entries are safe to add and check first.

When something is wrong

SymptomWhat to check
Web page does not load systemctl status ansiweb nginx, then curl -skI https://localhost/login on the server. If that works but other machines cannot reach it, it is a firewall or, on WSL, the port forwarding.
Certificate warning in the browser Expected: it is self-signed. Compare fingerprints with sudo openssl x509 -in /etc/ssl/ansiweb/server.crt -noout -fingerprint -sha256.
A PC shows as unreachable The prep script has not been run there, the IP is wrong, or the script had the wrong server address.
Credentials rejected The account password in AnsiWEB differs from the one used on that PC. Re-run the prep script there.
A PC cannot download installers On the PC, curl http://{{ server_ip }}/software/apps/ should answer 403. A timeout means a routing or firewall problem.
A PC shows as not reporting It has been off or unreachable since its last deployment. Test the connection from its page; the threshold is in Settings.
A driver fails with "the hash for the file is not present in the specified catalog file" Windows refuses an .inf its catalogue does not cover. Vendor packages often include helper .inf files that were never signed — Ricoh's oemsetup.inf is one — so AnsiWEB installs the ones Windows accepts, reports the rest, and only fails when none can be installed. If you want only particular ones, put a pattern such as MPC* in Only use these .inf files. If every .inf is refused, the package is partial, altered or for another Windows version: download it again from the vendor. Windows 10 and 11 enforce driver signing on a running PC and it cannot be turned off from here.
An uninstall left a program in place Either the pattern matched nothing, or the program has no silent uninstaller. The job log says which.
Signed out while working The idle timeout in Settings has elapsed. Watching a job log does not count as activity.
